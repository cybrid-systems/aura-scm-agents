# aura-scm-agents

An automotive supply-chain **multi-agent** scenario built on [Aura](https://github.com/cybrid-systems/aura) `orch:*`
primitives, plus the **EDSL policy evolution loop** (locate → observe → `mutate:rebind` with a reason → gate →
re-run/compare → `ast:snapshot` → rollback → audit).
Everything runs on deterministic mock data (EDI, inventory, a multi-tier BOM/supplier graph, claims history).
An optional LLM step writes the planner-facing explanation only; it never makes the decision.

## Quick start

```bash
# needs docker + an Aura build (build-rel/aura); tested on Aura main 235bcfa6b
export AURA_BIN=/path/to/aura/build-rel/aura
python3 scripts/run_demo.py            # -> results/demo.json, results/demo.md (~2.5 s)
python3 -m unittest tests/test_scenario.py
# optional prose (keys are read from files, never printed):
python3 scripts/llm_explain.py --provider deepseek                      # DeepSeek-V4.1-Flash, key file $DEEPSEEK_KEY_FILE
python3 scripts/llm_explain.py --provider minimax --env-file minimax.env # MiniMax-M3.1-Flash, $MINIMAX_API_KEY_FILE
```

`scripts/run.sh` runs the program inside `ghcr.io/cybrid-systems/dev:v1.0.9` (the build image; host glibc may be
too old). Set `AURA_NO_DOCKER=1` to run the binary directly. It concatenates `aura/*.aura` modules ahead of
`aura/main.aura` because, in `--load` mode, definitions made by `(load ...)` are not visible to the loading file.

## The story (maps to the PPT)

| 2. Demand & Arbitration explains the change | exposure 910k → `should-arbitrate?` = #t, hypothesis "customer pull-in, not forecast miss"; triggers Risk agent-to-agent | `orch:spawn-agent :attach-mailbox`, `orch:agent-send/recv` |
| 3. One scoped task per node computes days-of-cover/shortfall; `expedite-response` picks the action | `orch:scope-spawn`, `orch:scope-join-all` |
| 4. Profit Forensics | 8 historical events analysed under a collect-all supervision policy; one malformed record (OPS-007) is isolated (`partial ok=7 err=1`), leakage chains ranked (late EDI pull-in 60k, unnecessary PPAP switch 58k, SUP-T2-C lead-time miss 37k, forecast bias 33k) | `orch:compose-workflow 'collect-all`, `orch:supervise-batch` |
| 5. Claims & Recovery | `claim-root-cause` over 48 claims, recovery opportunity, prevent/recover rules | mailbox evidence hand-off Forensics → Claims |

| 7. Human in the loop | arbitration/expedite/cost > 100k → route to planner. CASE-1 approve: staged execution tasks complete. CASE-2 reject: `orch:scope-cancel-all` (6 cancelled) and the tasks abort | `orch:scope-spawn`, `orch:scope-cancel-all`, `orch:scope-join-all` |
| 8. Decision package + audit | priority list, actions, conflicts, leakage chains, claims, rules, execution status, full audit trail (who / when / what / why / before→after) | — |

## The three EDSL policies (and how they were adapted)

The policies live in the **Aura workspace** (`set-code` + `eval-current`), not in the program, so they can be
located, rebound, snapshotted and restored at run time. Files: `aura/policies/<name>.{v1,v2,bad}.aura`.

| policy | v1 (as given) | v2 (mutation, reason recorded verbatim) |
|---|---|---|
| `should-arbitrate?` | `abs(pct) > 0.15`, exposure > 500000, not frozen | `> 0.22`, exposure > 800000, not frozen, **and `high-confidence?`** — reason "阈值从15%调至22%，库存门槛提高，增加置信度过滤，减少误报" |
| `claim-root-cause` | forecast branch: `(and forecast-bias? (> bias-amount 0.1))` | forecast branch: `(or forecast-bias? market-signal-mismatch?)` — reason "增加市场信号不匹配作为预测误差判定条件" |
| `expedite-response` | high & days<5 → alert planner; ≥medium → alternative supplier; else monitor | medium → **`propose-internal-rebalance`** — reason "medium风险改为优先内部再平衡，降低不必要的供应商切换" |

Adaptations needed to run the user-supplied snippets on Aura (documented, not hidden):
1. **Accessors**: `change-pct`, `frozen-horizon?`, `high-confidence?` (confidence ≥ 0.7), `edi-increase?`,
   `supplier-lead-time-miss?`, `forecast-bias?`, `bias-amount`, `market-signal-mismatch?` are defined in
   `aura/policies/helpers.aura` over hash events and are installed in the workspace with the policies.
2. **Risk levels**: `(>= risk-level 'high)` is a type error in Aura (symbols are unordered) → `risk-rank` maps
   high/medium/low to 3/2/1 and the policy compares ranks.
3. **Actions as data**: `(alert-planner) (immediate-expedite-review)` became `(list 'alert-planner 'immediate-expedite-review)`;
   the Risk agent turns the action list into a costed proposal.
4. **Call sites**: thin workspace entry points (`demand-decide`, `claims-classify`, `risk-respond`) are what the agents
   call and what `query:calls` / `(query :def-use ...)` find before a mutation.
5. **Symbol comparison**: policy results are compared with `eq?`. Before aura#4727 (fixed in 88ba4e1fe) a symbol
   returned by a workspace function was not `eq?` to a quoted symbol (`probes/workspace-symbol-eq.aura`) and the demo
   compared by name; that workaround is gone.

### Evolution loop and results (deterministic, `results/demo.md`)

For each policy: locate (`query:calls`, def-use) → snapshot → metrics on history (v1) → `mutate:rebind` with the
reason → `eval-current` → gate → snapshot → a deliberately **bad** mutation (also with a reason) → gate fails →
`ast:restore` to the last good snapshot → metrics re-checked equal to v2. A syntactically broken rebind is refused
up front (parse gate). Gates: arbitration recall ≥ 0.8 and false-arbitration rate not worse; claims accuracy and
recovered amount not worse; expedite stockouts and cost not worse.

## Automatic evolution: swarm search over the policies (PSO + ACO, fibers, COW overlay)

`aura/search.aura` searches the policy space on its own and compares what it finds with the hand-written v1 and v2.
The searchers are std/pso, which tunes the continuous knobs, and std/ant pheromone trails, which choose structural
mutations. Each candidate is scored in its own fiber.

```bash
# host mode (no docker): AURA_LIBDIR = a dir with a new-enough glibc/libstdc++ + ld-linux-x86-64.so.2
export AURA_BIN=/path/to/aura/build-rel/aura AURA_STDLIB=/path/to/aura/lib [AURA_LIBDIR=...]
python3 scripts/run_search.py            # N = 0,1,4,8,16 + one commit run at N=8 -> results/search.{json,md}, search-provenance.jsonl
SCM_SEARCH_N=8 scripts/run_search.sh     # one run, raw @@key=value lines
python3 -m unittest tests/test_search.py # parse tests; e2e (tiny budget) when AURA_BIN/AURA_STDLIB are set
```
Knobs: `SCM_SEARCH_N` (fibers per wave, 0 = serial), `SCM_SEARCH_SEED`, `SCM_PSO_POP/GENS`, `SCM_ACO_ANTS/ITERS`, `SCM_EVAL_REPS`,
`SCM_NOISE_P` (share of candidates that get a deliberate defect, to exercise the gate), `SCM_STAGES` (default `aco,pso,aco`), `SCM_COMMIT`.

**Search space.**
* `should-arbitrate?`: the change threshold (0.15), the exposure threshold (500000) and the confidence cut (PSO), plus which of the
  four conditions are on (ACO).
* `claim-root-cause`: the bias threshold (PSO), plus branch order, supplier condition, demand condition (bias / bias-or-market / ...)
  and default (ACO).
* `expedite-response`: the inventory-days cutoff (PSO), plus the action per risk level (ACO).

Each stage starts from the policy's current best, so thresholds and structure can co-adapt.

**Per candidate.** mutate → gate (paren balance and parse, quoted-number lint, compile, output type/shape on every back-test row) →
20 back-test runs on the mock metrics → discard. One provenance row is recorded per attempt (`results/search-provenance.jsonl`:
stage, knobs, choices, injected defect, gate, reason, fitness, metrics, ms, error). Fitness is scalarized
(arbitration: recall − false-alarm rate, −1 if recall < 0.8; claims: accuracy + recovery rate; expedite: −cost(M) − 0.1·stockouts),
and a per-policy Pareto front of the raw objectives is kept next to it.

**Design (shared state lives in one place).** The coordinator (the main program) owns everything mutable: the RNG, candidate
table, global best, Pareto archive, the std/ant pheromone table and the std/pso swarm. It compiles each wave's candidates
(`eval` of the define → closure), spawns N fibers and blocks in `channel:recv`. A worker fiber only does the following:
`fiber:overlay-begin` → `fiber:overlay-define` of its closure (private, per-fiber COW overlay, aura#4715) → gate + score → `fiber:overlay-rollback` → `channel:send`
of one string message. It never calls `set!` or `hash-set!` on shared data, because concurrent `hash-set!` and `set!` are unsafe on this build (aura#4730). The coordinator
applies the messages sorted by candidate id, so results are bit-identical for every N. Only the coordinator touches the
workspace: it `mutate:rebind`s the winners (with a reason), checks the installed metrics equal the fiber's, then runs
two rollback drills (a worse candidate, and a truncated source), using `ast:snapshot`/`ast:restore`.

claims no speed-up.

### Limitations
* **No per-fiber workspace fork.** The overlay covers env bindings only. Candidates are therefore compiled with `eval` on the coordinator
  (string `eval` deadlocks inside parallel fibers, aura#4734), and only the coordinator rebinds the workspace. Compiling is serialized.
* **Workarounds for issues found here.** Fixed-arity callers on the fiber path, because rest-args lists get corrupted in parallel bodies (aura#4733).
  A quoted-number lint, because `and` swallows a type error in a non-last operand (aura#4735). A paren-balance guard, because `eval`/`mutate:rebind` accept
  unbalanced source (aura#4736). Commit drills run as top-level forms, because `ast:snapshot`/`restore` get slower when nested (aura#4737): 7 min 49 s nested vs ~1 s at top level.
* **std/pso is a global singleton without ask/tell** (aura#4739). The harness reads `pso:population`, scores the generation itself and feeds
  `pso:step!` a lookup. There is no multi-objective support (aura#4740) and the built-in `"parallel"` mode is unbounded and unisolated (aura#4741).
* **Synthetic labels; train-only search.** The table above is in-sample (train rows). Hold-out numbers for the swarm and the LLM arms
  are in the next section: swarm-only arbitration (train 1.0) drops to 0.889 on hold-out, the same as v2. The old "rebalance at every risk level"
  expedite optimum exploited the v1 mock cost model; cost model v2 (next section) closes it.

## LLM proposes, swarm fine-tunes (hold-out evaluation, GLM-5.3-Flash vs MiniMax-M3.1-Flash)

`scripts/llm_search.py` + `aura/llm-search.aura`. An LLM reads a policy's v1 source, its train metrics and up to 8 failing
train rows, and proposes **one structural edit plus a reason** as JSON `{"reason", "source"}`. The proposal goes through the same
gate / fiber / COW-overlay path as every swarm candidate. The swarm (ACO → PSO → ACO, coordinator-only state, aura#4730) then
fine-tunes the best LLM candidate. Its knobs are extracted generically from whatever source the LLM wrote: numeric literals
become PSO dims; `and`/`or` operands, `cond` clauses and action/label leaves become ACO decisions. Winners are committed with
`mutate:rebind` and a reason that carries the LLM reason and the swarm provenance.

```bash
export AURA_BIN=... AURA_STDLIB=... [AURA_LIBDIR=...]
python3 scripts/llm_search.py --models glm,minimax --k 4 --env-file ~/.config/aura-build/minimax.env   # ~35 min, 8 vCPU
python3 scripts/llm_search.py --models glm,minimax --k 4 --reanalyze   # re-summarize the last run, no LLM/Aura calls
python3 scripts/llm_search.py --models mock --seeds 1 --small          # deterministic mock LLM, no network
python3 -m unittest tests/test_llm_search.py
```
Providers (`scripts/llm_client.py`, OpenAI-compatible, keys read from files and never printed, logged or cached):
* `glm`: `glm-5.3-flash` on the coding-plan endpoint `open.bigmodel.cn/api/coding/paas/v4`, key `~/.glm-key`.
* `minimax`: `MiniMax-M3.1-Flash` (`SCM_MINIMAX_MODEL` overrides), key via `minimax.env`.
* `deepseek`.

Settings: max_tokens 8000, doubled once if a reasoning model returns empty content; transient 429/5xx/timeout/TLS errors are
retried 3×; at most 3 concurrent calls per provider. Responses are cached in `results/llm-cache/<model>/` keyed by the prompt hash,
so a rerun spends no tokens.

**Hold-out split.** `scripts/gen_data.py` draws a hold-out set from an independent seed (20261029): 120 EDI changes, 96 claims and
80 risk events. The train rows are byte-identical to before. All selection (best of K, swarm, commit choice) uses train rows only.
The hold-out rows are scored on the coordinator for reporting and never reach a prompt (prompts show train outcomes only).

**Expedite cost model v2 (the "rebalance everywhere" exploit is closed).** Each risk event now has a hidden outcome: the risk
materializes with p = .8 / .45 / .12 (high / medium / low), plus transfer and alternative-supplier lead times.
* `alert-planner` costs 35k and always arrives in time.
* `suggest-alternative-supplier` costs 45k and can arrive too late.
* `propose-internal-rebalance` costs 6k + 1.5k per earlier rebalance, can arrive too late, and falls back to the alternative
  supplier when there is no sister stock.
* `monitor` costs 0.

A stockout costs 150k. Fitness is normalized per 40 events. Rebalance-everywhere now scores −2.43 on train, worse than v1 (−2.565)
→ v2 (−2.10) → the optimum (≈ −0.7). The demo table above uses this model.

**Findings.**
* **LLM+swarm is the best arm on two of three policies.** On `should-arbitrate?`, MiniMax+swarm gets hold-out 1.000 (recall 1, no
  false arbitrations) and GLM+swarm 0.967, against 0.889 for v2 and swarm-only. On `expedite-response`, GLM+swarm gets −0.569
  vs −1.293 for swarm-only and −1.838 for v2; on the first seed its hold-out cost is 0.99M vs 2.29M (swarm-only) and 3.38M (v2).
  The LLM supplies the structure: GLM proposes "medium or high risk and < 6 days → `alert-planner`; < 9 days → rebalance;
  otherwise `monitor`". That three-band structure is outside the swarm's template space. The swarm then tunes the band edge
  (9 → 7 days on the first seed).
* **The swarm fixes LLM threshold guesses but can overfit.** MiniMax+swarm on `expedite-response` reaches better train fitness than
  MiniMax-only (−0.70 vs −0.95) but worse hold-out (−1.285 vs −1.038, gap 0.58, 7 stockouts on the first seed). On two seeds ACO switched *high* risk to
  `monitor`, which fits 40 train events and fails on hold-out. The hold-out split exists to show exactly this; a domain guard
  (e.g. high risk must never be `monitor`) belongs in the business gate.
* **Claims:** both LLMs broaden the forecast branch, and that ties v2 on train (2.0). On hold-out it is slightly worse (1.90 / 1.93
  vs 2.0) because a lowered bias threshold over-attributes. The swarm cannot break a train tie, and the commit choice may not look
  at hold-out data, so the committed GLM claims policy is not the hold-out-best one.
* **GLM vs MiniMax.**
  * Both always returned well-formed JSON (one GLM call failed with a TLS EOF).
  * Every MiniMax proposal passed the gate; one GLM proposal failed on output type.
  * MiniMax used 2.4× the output tokens (mostly reasoning) at a similar median latency (≈ 35-40 s; long tails up to ≈ 3 min for both).
  * GLM proposals are more aggressive and more often structurally new: its expedite edits beat everything.
  * MiniMax proposals are conservative, mostly v2-like: its arbitration edit plus swarm is the best on that policy.
* **Reason quality.** Both cite concrete metrics and failure rows.
  * GLM (expedite): "All 4 stockouts were medium-level with tiny inventory (2.8, 5.3d): alerting medium below 6 days fixes these
    (35000 vs 195000)…". It reasons from the outcome columns and is specific, but sometimes over-claims ("stockouts stay flat").
  * MiniMax (arbitration): "V1 makes 20 false arbitrations among 28 decisions (71.4%) while recall is 1.0; six of eight listed false
    positives have confidence below 0.7…". It is accurate and gate-aware ("preserving the 0.8 recall requirement") but rarely
    proposes more than one change.
* **Commits** (first seed): per model, trial commits of all 3 policies pass the business gate, installed metrics equal the fiber
  metrics, and v1 is restored. Then the train-best LLM+swarm per policy is kept: MiniMax for arbitration, GLM for claims and
  expedite. `mutation-log` has 6 entries.
  * Each rebind reason reads `LLM <model>: <reason> | swarm aco,pso,aco: llm-proposal #a -> base #b -> best #c (n evals, train fit x)`.
  * `results/llm-search-provenance.jsonl` has one row per LLM call (reason, source, tokens, latency, prompt hash, attempt id and
    gate result), one per Aura attempt, and one per commit (base/best attempt ids, swarm attempt range, before/after).

**Limits.**
* 3 seeds; the swarm reaches the same optimum on every seed, so its sd is 0.
* The LLM spread comes from sampling only (temperature 0.8, no API seed is passed).
* Labels are synthetic.
* About 8-11 candidates per run hit the fiber closure flake (aura#4745); retry + majority vote absorb it, counted as `llm.flakes`.
* Policy sources are read with a hand-written s-expression reader, because `quote` mangles special forms (aura#4743) and there is no
  datum reader (aura#4746).
* Fiber messages are strings because numbers hang `channel:recv` (aura#4744).

## Domain guards: business invariants as versioned workspace EDSL predicates (`aura/policies/guards.v1.aura`)

The invariants are not Python checks. They are Aura defines installed into the workspace next to the policies, so
`query:calls` / `current-source :workspace` can find them. They are versioned: `(guards-version)` is `"guards.v1"`, and a
`mutate:rebind` with a reason lands in the mutation log and the audit trail; `tests/test_guards.py` rebinds and restores a
guard. Each guard is `(lambda (f rows) -> violations)` over the candidate closure, the policy's **train** rows and a synthetic
domain grid (hold-out rows are never used). `(guard-registry)` lists `(name policy mode doc fn)`:

| guard | policy | mode | invariant |
|---|---|---|---|
| `exp.high-never-monitor` | `expedite-response` | hard (0) | high risk never maps to `monitor` (grid 0-20 inventory days) |
| `exp.critical-alert` | `expedite-response` | no-regress vs v1 (v1 = 4) | inventory-days < 2.0 with medium/high risk → at least `alert-planner` |
| `arb.frozen-never` | `should-arbitrate?` | hard (0) | recall on frozen-horizon changes stays 0 (frozen train rows + 36 synthetic frozen changes) |
| `claims.evidence-not-unknown` | `claim-root-cause` | hard (0) | a labelled row with evidence (lead-time miss, forecast bias, market mismatch) never returns `unknown` (v1 = 28) |

Where they run: the guards are part of the gate. On the fiber path they run on the **coordinator** after each wave
(`guard-post` in `aura/search.aura`), not in the fiber bodies. In-fiber guard closures abort or return `Void`/`<error>` on
Aura e6f4169e0; `SCM_GUARDS_IN_FIBERS=1` reproduces it. On the serial path (`SCM_SEARCH_N=0`) they run inside `score-once`.
Verdicts are identical for N = 0 and N = 2 (`tests/test_search.py`). Each guard is retried 3× (closure flake aura#4745). A
rejected candidate gets gate reason `guard`; counts are emitted per guard (`search.guard-rejects`, `llm.guard-rejects`).
`SCM_GUARDS=0` turns them off. The commit path (`evolve.aura`) also refuses a rebind whose guards fail.

**Re-audit of the previous 3-seed winners (eb43aef) against guards.v1** — the guards reject the MiniMax+swarm overfit:

| arm | `should-arbitrate?` | `claim-root-cause` | `expedite-response` |
|---|---|---|---|
| v1 / hand v2 | pass / pass | **fail** (28) / pass | pass / pass (critical-alert 4 = baseline) |
| swarm only | pass ×3 | pass ×3 | pass ×3 |
| GLM LLM-only | pass ×3 | reject ×3 (evidence-not-unknown 8) | reject ×3 (high-never-monitor 23/21/25) |
| GLM LLM+swarm | pass ×3 | reject ×3 (8) | reject ×3 (27) |
| MiniMax LLM-only | pass ×3 | reject ×3 (8) | reject 1/3 (seed 29: 25) |
| MiniMax LLM+swarm | pass ×3 | reject ×3 (8/4/8) | **reject ×3** (high-never-monitor 41/27/41, critical-alert 4/0/4) |

In a small guarded search (`SCM_SEARCH_N=2`, small budgets) the gate rejected 47 candidates by guard
(arb.frozen-never 8, claims 13, critical-alert 18, high-never-monitor 8), with the same verdicts at N=0.

## Honest notes / limitations

Validated on Aura main **e6f4169e0** (2026-10-28), `AURA_TIER_JIT=0` and `=1`: demo 10/10 runs per JIT with no lost
or missing scope task, tests 10/10.

* **No speed-up is claimed for the demo.** Since aura#4717 (P4/P5) fiber bodies run in parallel on worker threads,
  but the demo's agents share a blackboard hash and are pumped by one supervisor, so it is about orchestration
  semantics, not throughput (2.5 s, dominated by start-up). On e6f4169e0 concurrent `hash-set!` from parallel bodies
  is still unsafe (aura#4730) and a main-thread `fiber:yield` costs ~200 ms when a sibling is runnable (aura#4728).
* **Agent turns are pumped by the supervisor.** `orch:agent-recv` inside an `orch:spawn-agent` body (aura#4721) and
  in-process `orch:agent-ask` (aura#4722) are fixed upstream; the demo keeps the deterministic supervisor pump and its
  send/recv ask/reply (`kind|from|corr|body`) so runs are reproducible. Payloads must be strings, so structured data
  lives on a blackboard and messages carry keys.
* `orch:supervise-batch` now uses the default watch-scope (aura#4723 fixed): it waits for the batch and reports the
  real `partial ok=7 err=1` for the malformed record.
* Scope tasks lost after `orch:supervise-batch` / `orch:run-workflow` (aura#4725/#4726) are **no longer recomputed or
  executed inline**. A body that never ran is only counted and audited (`scope-task-missing`, `scope-task-lost`;
  `.exec-lost` / `.risk-missing` in `results/demo.json`), and `tests/test_scenario.py::test_no_lost_scope_tasks` fails
  if any appears. The standalone run-workflow probe still loses its tasks in ~2-3 of 20 runs on e6f4169e0, so #4726
  was reopened; the demo itself saw none in 20 runs.
* `orch:scope-cancel-all` now stops yielding bodies (aura#4724 fixed); the staged execution tasks still check the
  `decision` flag so a rejection is also visible in the blackboard.
* `string-split`/`filter`/`assoc` come from `std/list`, which Aura resolves relative to the current directory; the
  demo ships its own small helpers.
